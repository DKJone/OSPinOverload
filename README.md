# OSPinOverload

**为 WLoc / MyLoc 调整 iOS 定位服务的证书固定兼容设置。**

版本 **1.0.2 · build 10**。通过 TrollStore 安装，仅用于本人持有或明确授权的设备。

首页只展示操作结果和下一步，提供「启用定位兼容」「恢复原始设置」「仅检查，不修改」。检查、独立备份、副本恢复演练、实际修改和结果核对已融合为一次启用流程；技术记录放在「帮助与反馈」，不占用首页。

> 本工具不直接设置坐标，也不替代定位软件或其证书安装。它会降低 `gs-loc.apple.com` 与 `gs-loc-cn.apple.com` 的数据库证书固定约束，但不会关闭全局 TLS 验证。不能保证所有设备、系统版本或后续请求都可用。

## 开始使用

### 安装与准备

1. 在支持 TrollStore 的设备上，通过 TrollStore 安装 `OSPinOverload-1.0.2.tipa`(见release)。普通签名侧载不具备所需权限。
2. 先按 WLoc / MyLoc 的说明安装定位软件和证书，并完成系统信任设置；本工具不会安装或自动信任证书。
3. 保持手机解锁、存储空间充足，操作时让本工具留在前台。

最低部署版本为 iOS 15，不代表所有 iOS 15 及以上系统均受支持。目前真机效果仅在 **iPhone 11 / iOS 15.7.1** 验证；其他设备会先检查兼容条件。

### 启用

1. 点击「启用定位兼容」，阅读风险说明，确认「备份并启用」。
2. 等待检查、备份和核对完成。出现「已启用，请重启手机」后，**手动完整重启手机**，不是只重启应用或桌面。
3. 首次解锁后，打开 WLoc / MyLoc 设置位置并测试。

若只是想收集兼容信息，使用「仅检查，不修改」。检查不会提交规则变更，也不代表启用已经成功。

### 恢复

点击「恢复原始设置」，确认后等待出现「已恢复，请重启手机」，再手动完整重启手机。仅重启应用或桌面不能代替完整重启。

恢复使用这台设备的原始备份，插回原始规则内容和 rowid，不替换整个数据库。若系统更新、inode/权限或其他规则已经变化，将停止，避免覆盖新内容。重启可能改变挂载设备号；1.0.1 只在恢复时容许这一项跨会话变化，仍核对全部逻辑内容并在操作内固定当前文件身份。

**若提示「尚未恢复原始设置」，表示本次未提交恢复，重启不能补救此失败。** 保留备份，先发送反馈。1.0.0 真机恢复曾因挂载设备号变化在写入前被拒绝；1.0.1 真机反馈已确认恢复提交、独立核对通过、规则数恢复到 133，恢复引用已解除，用户确认功能正常。此规则数仅是测试设备的结果，不是其他设备的固定要求。

### 如何理解提示

| 提示 | 下一步 |
|---|---|
| 已启用，请重启手机 | 完整重启后再测试定位，不要重复启用。 |
| 兼容设置已启用 | 已保存上次成功结果，并推测手机此后重启过；可打开定位软件测试。不是对当前数据库的实时认证。 |
| 已恢复，请重启手机 | 完整重启，让系统重新加载原始规则。 |
| 尚未恢复原始设置 | 本次未提交恢复，重启不能代替恢复；保留备份并发送反馈。 |
| 已有待处理的备份 / 结果需要确认 | 不要再次启用、删除备份或手动覆盖数据库；先发送脱敏反馈，或按提示恢复。 |
| 未取得所需权限 | 确认通过 TrollStore 安装、已首次解锁。 |
| 暂未找到可调整的规则 / 操作未完成 | 可能无需处理或当前结构不兼容，分享反馈包协助确认，不强行修改。 |

「启用成功」表示数据库提交和独立读回通过；实际位置是否改变仍应在定位软件中验证。

### 从 0.3.0 升级

通过 TrollStore **覆盖安装同一应用**，不要先删除应用或 Media 下的项目目录。已有恢复引用会保留，并阻止重复启用；可读取旧报告，并允许在严格核对通过后恢复旧 build 的基线。

已经成功启用的设备不需要为了升级再应用一次。首页默认显示最近一次记录，不会自动运行 root 操作。

首页底部的「GitHub 项目主页」卡片展示完整地址 [https://github.com/DKJone/OSPinOverload](https://github.com/DKJone/OSPinOverload)，点击后交给系统浏览器或 GitHub 应用打开，可查看源码、使用说明和版本更新。仅点击时打开，不自动联网、上传反馈或触发诊断；规则操作期间入口暂时禁用。

## 反馈与隐私

首页右上角进入「帮助与反馈」：

1. 可先点「脱敏摘要」查看将分享的诊断字段。
2. 点击「分享脱敏反馈 ZIP」，确认后由系统分享面板选择接收软件，或存储到「文件」。已排除 AirDrop，以避开 iOS 15 真机确认的隔空投送图标渲染崩溃。
3. 同时向支持人员说明操作步骤、手机是否已重启、具体表现和测试时间。应用不会自动上传或联系任何服务器。

默认 ZIP 只有三个文件：

| 文件 | 内容 |
|---|---|
| `feedback.json` | 软件版本、报告来源版本、设备型号、系统版本、规则数量、检查名称/级别、提交阶段和核对结果 |
| `events.json` | 从已知阶段提取的固定事件名称；原始错误详情不会直接复制 |
| `PRIVACY.txt` | 数据收集范围与排除项 |

**不包含**坐标、WiFi/MAC、网络请求/响应正文、证书策略内容、设备唯一标识、session UUID、路径、原始日志或任何数据库/备份。采用字段白名单和固定事件投影，而不是对整份日志简单替换字符串。设备型号和系统版本仍会保留，请只向可信接收方分享。

ZIP 也保存在本机 `/var/mobile/Media/OSPinOverload/Exports/Feedback/`。系统分享使用明确 ZIP 类型的数据，不把受保护文件 URL 交给预览服务。若分享仍异常，可选择「高级诊断与本机导出 → 仅保存脱敏 ZIP」，完全不打开分享面板，再通过 Filza/USB 获取此 ZIP；**不要把原始证据目录误当作脱敏包**。

1.0.2 起，名称包含应用、版本、导出时间和随机短后缀，例如 `OSPinOverload-feedback-v1.0.2-20261106-110000Z-A1B2C3D4.zip`。`Z` 表示 UTC 时间，后缀只用于避免重复，不是设备或 session 标识。分享同时提供该名称的 ZIP 文件表示，避免只提供数据时部分接收软件使用泛化的 `File.zip`；接收软件仍可能自行改名。

高级菜单保留权限对照、备份/回滚预检和 USB 完整本机导出。完整导出包含原始日志与系统数据库，需额外确认，不会进入系统分享。旧 build 的完整导出需先重新运行只读检查；默认脱敏反馈可明确标注旧报告来源。

## 实现原理

### 为什么普通证书信任还不够

WLoc / MyLoc 使用本地 HTTPS 代理处理 Apple 定位请求。即使安装并信任自定义根证书，`locationd` 的附加证书固定策略仍可能要求 Apple 信任锚、叶证书或中间证书标记，导致在 HTTP 请求发出前以 -9807 / -1202 拒绝连接。

Apple 的受保护规则数据库位于：

```text
/private/var/protected/trustd/pinningrules.sqlite3
```

本工具只处理已确认的共享定位规则：

```text
policyName = AppleIssued
domainSuffix = apple.com
labelRegex = ^gs-loc$|^gs-loc-cn$
```

这是一行规则，对应两个主机名；不会清空规则表、修改其他域名或全局关闭 TLS。其他独立/硬编码策略仍可能生效。

### 受控修改与恢复

UIKit 控制器仅在用户确认后，使用 persona override 启动同一可执行文件的短生命周期 root worker。除既有基础权限外，仅增加已实验验证的 `com.apple.private.security.storage.trustd` 存储声明，不复制其他应用的整套权限。

启用流程：

1. 以只读连接和 SQLite backup API 生成一致性快照，检查完整性、结构、目标行及源文件身份。
2. 同步保存独立、不可覆盖的原始基线和摘要，在自有副本上删除目标行并演练恢复原始 BLOB 与 rowid。
3. 对活动数据库预检 READWRITE、BEGIN IMMEDIATE / ROLLBACK，确认基线仍一致。
4. 持久保存恢复引用，再在事务锁内比较完整 schema、admin、rules 与 rowid；只删除唯一目标行。
5. 确认无非目标变动后 COMMIT，再用独立连接读回核对；同步保存提交前后阶段。

恢复执行相反的单行插入，使用该设备备份中的原始 BLOB 和 rowid。仅当当前完整状态与预期相符才操作；已经完整恢复则只核对，不重复插入。提交结果未知时保留现场与恢复引用，不自动重试。

不调用任意 SQL 接口，不更改权限/属主，不用副本覆盖活动数据库，不自动清理 journal，不强制修复未知状态。

### 为什么建议重启

公开旧版 Apple 源码中存在按域名后缀缓存规则的逻辑；官方更新入口会清缓存，外部直接修改数据库不一定触发它。不同源码版本的缓存开关不同，不能用最新 `main` 直接代表旧系统。

本次设备在单行提交成功后立即复测仍遭证书拒绝，完整重启后定位修改恢复；日志也确认 `locationd` 验证结果为 0、握手完成、目标请求返回 HTTP 200。这支持旧进程状态需要刷新，但重启同时重建多个进程和连接，不能唯一归因于 trustd 的域名缓存。

软件只提示手动重启，不自动终止或重载 trustd/locationd，不注入服务，不拦截系统信任资产更新。

## SQLite 与设备兼容边界

兼容判断不绑定某台设备的 inode、UID、数据库大小、内容版本、规则总数或固定 policies 摘要：这些值都从当前设备读取，再用于本次基线与并发变动核对。支持已知五列的不同排列，`transparentConnection` 为 0 或 NULL 时保留其原始类型和内容，恢复保持原 rowid。

为避免“看似兼容、实际破坏恢复”，写入仍要求：

- schema 3、DELETE journal、无现存 `-wal` / `-shm` / `-journal`。
- 仅已知 admin/rules 两表，无 trigger/view，rules 为已知五列，无额外/隐藏/生成列且具有可恢复的 rowid。
- 两个主机匹配同一条已知共享规则，policies 为有效原始 BLOB。
- 文件 inode、权限、基线和事务内完整逻辑状态均一致；恢复允许跨重启的挂载设备号变化，但本次操作内的 device/inode 必须始终一致，启用仍严格绑定新基线的 device/inode。

只读诊断可以读取 WAL 的一致性快照；**受控写入暂不支持 WAL 或未知 schema**，不会为了兼容而切换 journal、忽略额外字段或猜测规则。这是安全拒绝，不应使用 Filza 强行替换绕过。

系统更新可能重建规则，使效果失效，也可能让旧基线不再适合恢复。遇到此情况先检查和反馈，不自动覆盖系统新内容。

## 已知限制与验证范围

- 真机单行提交、重启后两次目标请求成功和用户确认的位置修改已验证。1.0.0 的分享崩溃与恢复误拒绝经 1.0.1 修复后，用户确认功能正常；收到的真实脱敏 ZIP 也确认恢复 COMMIT/核对成功、恢复引用解除。分享正常属于用户实测反馈，不代表所有接收软件均已覆盖；该 ZIP 不包含重启时间或 TLS/定位请求，不能单独证明恢复后服务行为。
- 重启后的定位日志还出现过 6 次同目标的 TLS 前连接失败（-1000/EINVAL），原因尚未确定；不能保证所有后续请求成功，也不能仅凭 QUIC 标记归因。
- 系统还有空 MAC、偏好读取和 UI 警告，未证明由此数据库修改引起；脱敏结论见 [迭代记录](docs/ITERATIONS.md)。
- 不保证 GPS、基站、其他定位来源或任意第三方软件都会采用改写位置；不提供跨系统长期有效性承诺。
- 备份是改动前的数据库状态，不是系统更新前的“健康数据库”。不要删除 `/var/mobile/Media/OSPinOverload/Baselines/` 或 `Diagnostics/recovery-reference.json`。

## 构建与开发

需要 macOS、Xcode、Swift、`ldid`；USB 工具脚本使用 libimobiledevice 与 `afcclient`

```sh
swift test
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s Tests -p 'test_device_artifacts.py' -q
bash packaging/simulator_smoke_test.sh
bash packaging/build_tipa.sh
```

产物：`Build/OSPinOverload-1.0.2.tipa`。`bash packaging/copy_tipa_to_device.sh --no-build` 仅 USB 复制、回读校验和清理已识别旧包，不会安装或修改规则。

原始证据与打包产物位于忽略的 `Build/`，不提交。报告格式、开发者 USB 导出与恢复协议见 [DIAGNOSTICS](docs/DIAGNOSTICS.md)，版本记录见 [CHANGELOG](CHANGELOG.md)。
